# Style Guide проекта "React"

99_Style_Guide_HTML.md

Версия: 1.0

---

## 1. Общая концепция книги

Это не классический учебник.

Основная идея проекта — практический справочник, в который удобно возвращаться спустя месяцы или годы.

При написании материала придерживаемся следующих принципов:

- минимум "воды";
- максимум практики;
- объяснение простым языком;
- реальные примеры;
- лучшие практики;
- типичные ошибки;
- советы из практики;
- материал должен легко использоваться как шпаргалка.

Книга должна отвечать не только на вопрос **"что это такое?"**, но и **"как этим пользоваться?"**.

---

## 2. Структура книги

Каждая глава состоит из:

1. Основной материал.
2. Итоги главы.
3. Шпаргалка главы.

Это правило действует для всех глав.

---

## 3. Структура HTML главы

Каждая новая глава начинается одинаково.

```html
<section class="chapter" id="chN">

    <h1>Глава N. Название главы</h1>

</section>
```

Секция сразу закрывается.

Все подразделы вставляются позже.

---

## 4. Новый раздел

Каждый раздел начинается одинаковым комментарием.

```html
<!-- ===== Название раздела ===== -->

<h2 id="chN-section-name">📜 Название раздела</h2>
```

Используем именно такой комментарий.

Не используем длинные комментарии из нескольких строк.

---

## 5. Именование id

Используется сквозная схема.

Пример:

```html
ch1-introduction
ch2-install-node
ch3-jsx
```

Меню и разделы должны иметь одинаковые id.

---

## 6. Sidebar

Для каждого раздела обязательно существует пункт меню.

data-target всегда совпадает с id заголовка.

---

## 7. Info Box

Используются только существующие классы.

```html
info-box note
info-box success
info-box warning
info-box danger
```

Структура всегда одинаковая.

```html
<div class="info-box note">
    <div class="info-box-title">💡 Совет</div>
    <p>Текст...</p>
</div>
```

После info-box-title пустая строка НЕ ставится.

Не использовать дополнительные классы вроде:

```html
info-content
```

---

## 8. Таблицы

Любая таблица обязательно помещается внутрь

```html
<div class="table-wrapper">
```

Полная структура

```html
<div class="table-wrapper">
    <table>
        <thead>
            <tr>
                <th>...</th>
                <th>...</th>
            </tr>
        </thead>

        <tbody>

            <tr>
                <td>...</td>
                <td>...</td>
            </tr>

            <tr>
                <td>...</td>
                <td>...</td>
            </tr>

        </tbody>
    </table>
</div>
```

Между логическими блоками оставляются пустые строки.

---

## 9. Списки

Используются компактные списки.

Правильно:

```html
<ul>
    <li>...</li>
    <li>...</li>
    <li>...</li>
</ul>
```

Неправильно:

```html
<ul>

    <li>...</li>

    <li>...</li>

</ul>
```

Между `<li>` пустые строки не ставятся.

---

## 10. Блоки кода

Используется только

```html
<div class="code-block"><code>
...
</code></div>
```

Не использовать

```html
<pre><code>
```

---

## 11. Комментарии в коде

Комментарии всегда оформляются так:

```html
<code class="comment">// комментарий</code>
```

Пример

```html
<div class="code-block"><code>const name = "React";

<code class="comment">// вывод значения</code>

console.log(name);</code></div>
```

Обычные комментарии

```js
// комментарий
```

не используются.

---

## 12. Консоль

Вывод результата оформляется так

```html
<pre class="browser">
...
</pre>
```

Для shell-команд

```html
<pre class="sh">
...
</pre>
```

## 13. Экранирование HTML

Во всех блоках кода HTML обязательно экранируется.

Используем

```html
&lt;
&gt;
```

Например

```html
&lt;div&gt;
```

а не

```html
<div>
```

## 14. Форматирование кода

Код должен быть читаемым.

Допускаются пустые строки между логическими блоками.

Например

```js
const user = {

    name: "Tom",

    age: 25

};

function App() {

    ...

}
```

## 21. Форматирование блоков кода

- Не добавлять пустые строки внутри коротких функций.
- Разделять пустой строкой только логические блоки (переменные, функции, export).
- Весь код внутри `<code>` начинается с первой колонки, без общего левого отступа.
- Использовать обычный стиль форматирования VS Code / Prettier.
- Для комментариев использовать:
`<code class="comment">// ...</code>`
- Не делать «воздушный» код без необходимости.

### 21.1 Не добавлять пустые строки внутри коротких функций

Было:

```jsx
function Header() {

    return <h1>Header</h1>;

}
```

Должно быть:

```jsx
function Header() {
    return <h1>Header</h1>;
}
```

### 21.2 Разделять только логические блоки

То есть:

объявления переменных;
объявления функций;
экспорт.

Например:

```jsx
export const VERSION = "1.0";

export function Header() {
    return <h1>Header</h1>;
}

export function Footer() {
    return <footer>Footer</footer>;
}
```

или

```jsx
function Header() {
    return <h1>Header</h1>;
}

export { Header };
```

### 21.3 Не делать общий отступ внутри `<code>`

Сейчас я иногда генерирую так:

```jsx
<div class="code-block"><code>import Header from "./Header";

    function App() {

        return (
```

Из-за этого весь код съезжает вправо.

Правильно:

```jsx
<div class="code-block"><code>import Header from "./Header";

function App() {
    return (
        ...
    );
}</code></div>
```

То есть внутри `<code>` отсчет начинается с первой колонки, независимо от того, что сам `<div>` находится на 16–20 уровне отступа HTML.

### 21.4 Отступы должны быть только логическими

То есть:

```jsx
function App() {
    const title = "React";

    function handleClick() {
        console.log(title);
    }

    return (
        <div>
            <h1>{title}</h1>
        </div>
    );
}

export default App;
```

А не:

```jsx
function App() {

    const title = "React";

    function handleClick() {

        console.log(title);

    }

    return (

        <div>

            ...
```

### 21.5 HTML-разметку → сразу готовым HTML, без writing block;

## 22. Формирование схем

Сетевые схемы должны быть простыми, читаемыми и выполненными в едином стиле.

Основной принцип:

- простые линейные схемы допускается оформлять через `<pre class="browser">`;
- сетевые топологии и схемы, где важно точное расположение устройств и соединений, оформляются через inline SVG;
- для новых полноценных сетевых топологий предпочтительно использовать SVG;
- не выравнивать сложные схемы вручную пробелами.

### 22.1 Когда использовать `<pre>`

`<pre class="browser">` используется для простых схем, где расположение элементов не требует точного позиционирования.

Например:

```html
<pre class="browser">
Application
    │
    ▼
   TCP
    │
    ▼
   IP
    │
    ▼
 Ethernet
</pre>
```

Также `<pre>` можно использовать для простого направления обмена:

```html
<pre class="browser">
Client ──────── запрос ────────► Server
Client ◄──────── ответ ───────── Server
</pre>
```

Не использовать `<pre>` для сложных сетевых топологий, если для выравнивания приходится вручную добавлять большое количество пробелов.

---

### 22.2 Когда использовать SVG

Inline SVG используется, если в схеме важно:

- точное расположение устройств;
- несколько соединительных линий;
- ответвления;
- несколько коммутаторов или маршрутизаторов;
- отображение топологии сети;
- подписи интерфейсов или соединений;
- визуальное разделение частей сети;
- стабильное отображение при изменении ширины окна.

Например:

```text
PC1 ──┐
      │
PC2 ──┼── Switch ─── Router ─── Internet
      │
PC3 ──┘
```

Такую схему предпочтительно выполнять через SVG.

---

### 22.3 SVG вставляется непосредственно в HTML

По умолчанию схемы вставляются как inline SVG:

```html
<div class="network-diagram">

    <svg viewBox="0 0 650 190"
         xmlns="http://www.w3.org/2000/svg"
         role="img"
         aria-label="Описание схемы">

        ...

    </svg>

</div>
```

Не создавать отдельный `.svg`-файл без необходимости.

Это позволяет сохранить справочник максимально автономным:

```text
Network.html
```

должен содержать все основные схемы непосредственно внутри документа.

---

### 22.4 Общий контейнер схемы

Каждая SVG-схема помещается внутрь:

```html
<div class="network-diagram">
    ...
</div>
```

Для всех сетевых схем используется один общий набор CSS-правил.

Базовый вариант:

```css
.network-diagram {
    margin: 18px 0;
    padding: 16px;
    border: 1px solid var(--border);
    border-radius: 8px;
    overflow-x: auto;
}

.network-diagram svg {
    display: block;
    width: 100%;
    max-width: 700px;
    height: auto;
}

.network-diagram line,
.network-diagram path {
    stroke: currentColor;
    stroke-width: 2;
    fill: none;
}

.network-diagram text {
    fill: currentColor;
    font-family: inherit;
    font-size: 16px;
}

.network-diagram .diagram-label {
    font-size: 14px;
}
```

Если позже стиль схем изменяется, CSS меняется централизованно, а не отдельно для каждой схемы.

---

### 22.5 Использовать `viewBox`

Каждая SVG-схема должна иметь `viewBox`.

Например:

```html
<svg viewBox="0 0 700 250"
     xmlns="http://www.w3.org/2000/svg">
```

Не задавать расположение схемы относительно конкретного разрешения экрана.

`viewBox` используется для сохранения пропорций и корректного масштабирования схемы.

---

### 22.6 Единые классы элементов

По возможности использовать одинаковые классы:

```html
diagram-device
diagram-link
diagram-label
diagram-wireless
diagram-group
```

Назначение:

```text
diagram-device      устройство или его подпись
diagram-link        проводное соединение
diagram-label       дополнительная подпись
diagram-wireless    беспроводное соединение
diagram-group       логическая область сети
```

Не создавать новый CSS-класс для каждой отдельной схемы без необходимости.

---

### 22.7 Соединения

Проводные соединения оформляются линиями:

```html
<line class="diagram-link"
      x1="..."
      y1="..."
      x2="..."
      y2="..." />
```

Для сложных соединений допускается использовать `<path>`.

Соединительные линии должны:

- быть хорошо видны;
- не пересекать текст без необходимости;
- иметь одинаковую толщину в пределах справочника;
- визуально показывать, какие устройства действительно соединены.

Не использовать пробелы и псевдографику для точного позиционирования соединений в сложной топологии.

---

### 22.8 Подписи устройств

Названия устройств должны быть короткими и понятными.

Предпочтительно:

```text
PC1
PC2
SW1
R1
Server
Access Point
Internet
```

Если схема учебная и устройство встречается впервые, допускается более понятная подпись:

```text
Компьютер 1
Switch
Router
Web Server
```

По мере усложнения материала допускается переход к стандартным коротким обозначениям:

```text
PC1
SW1
R1
R2
SRV1
```

---

### 22.9 Цвета

Не использовать цвет как единственный способ передачи смысла.

Схема должна оставаться понятной:

- в светлой теме;
- в тёмной теме;
- при печати;
- при чёрно-белой печати.

По возможности использовать:

```css
stroke: currentColor;
fill: currentColor;
```

чтобы схема автоматически адаптировалась к теме документа.

Цветовые выделения допускаются только как дополнительный визуальный элемент.

---

### 22.10 Размер схем

Схема не должна искусственно растягиваться на всю ширину страницы.

Использовать разумный `max-width`:

```css
.network-diagram svg {
    width: 100%;
    max-width: 700px;
    height: auto;
}
```

Для большой топологии допускается увеличить `max-width`.

При уменьшении окна схема должна масштабироваться с сохранением пропорций.

---

### 22.11 Доступность

Для содержательной SVG-схемы использовать:

```html
role="img"
aria-label="Краткое описание схемы"
```

Например:

```html
<svg viewBox="0 0 700 250"
     xmlns="http://www.w3.org/2000/svg"
     role="img"
     aria-label="Три компьютера подключены к коммутатору">
```

`aria-label` должен кратко передавать смысл схемы, а не перечислять все SVG-элементы.

---

### 22.12 Схема не заменяет объяснение

Схема является дополнением к тексту.

Перед схемой или после неё должно быть объяснено:

- что изображено;
- на что обратить внимание;
- какой принцип демонстрирует схема.

Не оставлять сложную топологию без пояснения.

---

### 22.13 Не перегружать схемы

Одна схема должна объяснять одну основную идею.

Лучше:

```text
Схема 1 → работа Switch
Схема 2 → работа Router
Схема 3 → путь пакета
```

чем одна огромная схема, одновременно показывающая все технологии главы.

Если для понимания схемы требуется долго изучать легенду, вероятно, её следует разделить на несколько схем.

---

### 22.14 Постепенное усложнение

При объяснении новой темы схема развивается вместе с материалом.

Например:

```text
PC1 ─── Switch ─── PC2
```

затем:

```text
PC1 ───┐
       ├── Switch ─── Router
PC2 ───┘
```

затем:

```text
LAN 1 ─── Router ─── LAN 2
```

Не показывать сложную итоговую топологию раньше, чем объяснены её основные элементы.

---

### 22.15 Главное правило

Использовать самый простой формат, который корректно передаёт смысл.

```text
Простая последовательность
        ↓
      <pre>

Топология / точное расположение
        ↓
    inline SVG
```

Не использовать SVG там, где достаточно нескольких строк текста.

Не использовать `<pre>` там, где схема начинает зависеть от ручного выравнивания пробелами.

### 22.16 Проводные и беспроводные соединения

Для сетевых схем используется единое обозначение:

- сплошная линия — проводное соединение;
- пунктирная линия — беспроводное соединение.

```css
.diagram-link {
    stroke: currentColor;
    stroke-width: 2;
}

.diagram-wireless {
    stroke: currentColor;
    stroke-width: 2;
    stroke-dasharray: 7 5;
}
```

Не использовать ))), ~~~ и другие символы псевдографики для обозначения беспроводного соединения внутри SVG.

```html
<!-- Наконечник общей стрелки -->
<defs>
    <marker id="arrowhead"
            markerWidth="8"
            markerHeight="8"
            refX="6"
            refY="4"
            orient="auto"
            markerUnits="strokeWidth">

        <path d="M 0 0 L 8 4 L 0 8 Z"
            fill="currentColor" />
    </marker>
</defs>

<!-- Общая стрелка -->
<line class="diagram-wireless"
    x1="300" y1="105"
    x2="310" y2="105"
    marker-end="url(#arrowhead)" />

<!-- Устройства -->
<text class="diagram-device" x="40" y="45">Ноутбук</text>
<text class="diagram-device" x="40" y="110">Смартфон</text>
<text class="diagram-device" x="40" y="175">Планшет</text>
```
